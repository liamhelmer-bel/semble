## Part 1: Phase-1 PR (script and results report)

### Must fix before approval

**P1. The module docstring is false.** `tiered_resource_spike.py` says "Embeddings are synthetic; no model is downloaded." `source_embed()` loads and runs the real `potion-code-16M-v2` model. The "no download" part is true; "synthetic" is not.
- Fix: say that synthetic vectors are used everywhere except `embed` mode, which runs the cached real model.

**P2. Token truncation is understated as "may".** Each 4 KiB window of `def identity(value):\n    return value\n\n` holds about 105 copies of a 39-byte unit, at roughly 10–12 tokens each. That is about 1,000+ tokens against `max_length=512`, so roughly half of every window is almost certainly dropped. I believe model2vec also cuts the input string to about `max_length × median_token_length` characters before tokenizing. If so, the measured throughput of about 14 MB/s overstates full-coverage throughput by about 2×. Please verify this rather than take my word for it.
- Fix: count tokens per window with the tokenizer alone (no embedding) on this fixture. Also count on two or three token-dense samples, such as minified JS, base64/hex and a JSON dump. Report tokens per KiB, then correct the wording and the throughput interpretation. This number also drives ADR blocker A1.

**P3. The table's "Seconds" column has no single meaning and is not generated by any code.**
- `baseline` with a 100 KB fixture returns `build_seconds`, `load_seconds` and `query_seconds`, not `seconds`.
- `vicinity` and `mapped` return `load_seconds` and `query_seconds`.
- Loading plus normalizing 128 MiB in 4.3 ms is implausible, so that row is presumably `query_seconds`. The reader cannot tell.
- The baseline exclusion rows for 4 MB–1 GB were run but are left out of the table.
- Fix: add a `--table` renderer that reads the JSON, or split the column into named build/load/query/op columns. Include the exclusion rows.

**P4. Neither the filesystem nor the storage type is recorded.** The report says "physical writes", but `TemporaryDirectory()` writes to `/tmp`, which is tmpfs on some distributions.
- On tmpfs, the fixtures use RAM (about 2.5 GB), and mapped pages show up as `RssShmem`, not `RssFile`. The `mapped` file-RSS column would then measure nothing.
- Fix:
  - Record the filesystem type of the temp directory in the JSON.
  - Sample `RssShmem` as well.
  - Accept `--tmpdir`.
  - Check free space with `shutil.disk_usage` before writing 2.5 GB.

**P5. The prior review's experiments have no recorded outcome.** The report lists what is *not* claimed, but not what happened to each experiment Opus asked for:

| Experiment | Status |
| --- | --- |
| #1 real-repo inventory | Missing, and it was listed first because it could simplify the design. It is cheap: counts of eligible-extension files above 1 MB, 100 MB and 1 GB, with no paths. |
| #5 comparison with `rg` and case-folded copies | Not done, no reason given. |
| #7 cold cache via `fadvise` | Not done, no reason given. Note: `fsync` first, because `POSIX_FADV_DONTNEED` does not drop dirty pages, and it does nothing on tmpfs. |
| #2, #8, #9 | Deferred, with reasons in the ADR. |

- Fix: add a done / deferred / rejected table with a reason for each. Run the inventory before ADR approval.

### Should fix (not blocking)

- **P6. Peak-RSS method.** 5 ms sampling cannot see 4–8 ms operations; the report admits this. There is an exact alternative that needs no root and works in each worker:
  1. After imports and model load, write `5` to `/proc/self/clear_refs` to reset `VmHWM`.
  2. Run the operation.
  3. Report `VmHWM` and `RssAnon`/`RssFile`/`RssShmem` *before unmapping*.

  This turns the vicinity and mapped comparison from inference into measurement. It also separates per-batch embedding memory from the roughly 107 MiB of model load.
- **P7.** `baseline()` queries the pre-save `dense`, not `loaded`, so "cache roundtrip and query" does not hold. Query through `loaded`.
- **P8.** `baseline()` saves `cache/` *inside* the indexed root, so repeat 1 indexes a different tree from repeat 0. The results match, so it was probably ignored, but save outside the root.
- **P9.** The model path is hard-coded to `~/.cache/huggingface/hub` and ignores `HF_HOME` and `HF_HUB_CACHE`. Use `huggingface_hub` with `local_files_only=True` and semble's default model constant.
- **P10.** "Sampled every 5 ms" is really a 5 ms sleep plus a recursive `/proc` scan per sample. Say "≥5 ms".
- **P11.** State the measured `model.dim`. B1 asked for it to be confirmed, and the ADR's 256 depends on it.
- **P12. Fixture diversity.** One repeated 39-byte unit gives near-100% hits in the BPE word cache. Throughput on real code will be lower. A cheap fix is a fixture made by repeating the repo's own `src/`.
- **P13. Carry-forward bug, not a spike blocker.** `scan()` uses `overlap = data[-(len(needle) - 1):]`. For a 1-byte term that is `data[-0:]`, which is the whole buffer: overlap grows without bound and matches are double-counted. The production scanner needs `max(len - 1, 0)` and a test for it.
- **P14.** `psutil` is imported at module level but not declared anywhere. If CI's ruff or mypy covers `benchmarks/`, add a `bench` extra or exclude the directory.

## Part 2: ADR

### Blockers for human approval

**A1. Vectors that are stored but cannot be searched.**
- "Vector bytes examined per query" is 256 MiB.
- The ADR's own best case for one 1 GB middle-tier file is about 250 MB of float32 vectors. With realistic token splitting (P2), that becomes about 500–600 MB.
- So **a single maximum-size middle-tier file cannot be fully searched semantically in one query**, and anything past the first 256 MiB of vectors is never reached. Yet the ADR stores those vectors with no total limit.
- The ADR also does not say in what order vectors are scanned once the budget runs out.
- Fix: make storage and searchability agree. Choose one:
  - raise the per-query vector budget (a warm scan of 512 MiB to 1 GiB is well within 2 s);
  - lower the middle-tier ceiling;
  - set a total vector limit equal to what a query can scan.

  Then state the scan order and how partial coverage is disclosed.

**A2. Disk safety.** "Abort publication when disk is full" means the disk is filled to 100% first. Other processes are hurt, and a single first MCP query can trigger it.
- The rebuttal also misdescribes the earlier advice. Opus proposed demotion *with reporting*, not silent demotion.
- Fix, which still keeps "no demotion":
  - Before staging, project the bytes needed: eligible middle-tier bytes × an upper bound on vector bytes per source byte, plus references, any retained clone, and duplicates across content scopes.
  - Refuse to start if the projection exceeds free space minus a reserve. Report coverage `disabled` with a disk reason.
  - The human should explicitly approve the absence of a quota.

**A3. The size estimate needs a range.** "About 250 MB per GB" is a best case. For token-dense content, a 512-token window can be about 1 KiB or less, so vectors can approach or exceed the source size. B1 warned about exactly this.
- Fix: state best, measured and worst-case ratios using the P2 token counts.
- Also update the reference record size: as specified it is 52 bytes packed, not the earlier 36.

**A4. Several processes share the cache, and the ADR only covers one.** In Liam's setup, the Claude and Codex MCP servers, and the CLI, can all use the same cache root. "Readers pin generations", "serialize publishers" and "1 builder per MCP manager" read as in-process guarantees only.
- Fix: specify the mechanisms:
  - a lock file per cache key for building and publishing, so two servers do not both build;
  - a shared lock held per reader on each generation, with cleanup taking a non-blocking exclusive lock;
  - readers opening every file of a generation when they pin it, not lazily, so cleanup cannot remove files from under them.

**A5. The literal scanner's read path is unspecified.** The `SourceReader` contract is good. The `LiteralScanner` section does not say it uses it, and B4 asked that it do so.
- Fix: the scanner opens files through the same verified, no-follow path. It checks the fingerprint before and after each file and drops snippets from any file that changed mid-scan.
- Also state that classification excludes symlinked oversized files, or records them as such. Otherwise they count as eligible but can never be read.

**A6. Ranking contract.**
- (a) "Run the existing normal-only search unchanged" is ambiguous. Does it apply only when no oversized files exist, or does normal ranking always run unchanged before merging? If it is the first, adding one 2 MB file reorders every normal result, because the existing fusion is replaced by RRF. State which, and state that behavior change.
- (b) "Same model, so cosine scores are comparable" ignores length. model2vec mean-pools token vectors, so 4 KiB windows drift toward the corpus mean compared with 750-character chunks, which biases cross-tier cosine. Keep the single dense ranking, but name this as a release-gate risk with a ready fallback, such as a per-tier quota or calibration.

### Clarifications (not blocking)

- **"Bump format 2"**: say from which version to which. Say that old-layout caches stay orphaned in place (consistent with no purge) and that their bytes are reported. Add a release-gate test for a 0.7.3 install and the fork sharing one cache root; the global config pins `semble[mcp]==0.7.3`.
- **Remote URLs**: keeping a pinned clone adds disk, lifecycle and security surface. I recommend disabling both oversized tiers for remote URLs in v1 (coverage reason `disabled`) and deferring clone retention.
- **Delivery order**: state why the scanner, which is cheap and covers both tiers, stays in phase 5 instead of moving ahead of stages 3–4.
- **Source retry**: say it only targets an *already published* newer generation and never builds inline.
- **`ctime_ns` on Windows**: there it means creation time; state what is compared instead.
- **Stats**: answer Opus's point that `file_chars` inflates savings for middle-tier hits.
- **Path-only BM25 documents** for oversized files: accept or reject explicitly.
- **"At most 1 GiB combined"**: two queries × (256 + 256 MiB + 0.5 MiB hydration) slightly exceeds 1 GiB. Reword.
- **CI**: making CI run on PRs into `fork-main` should be a precondition for the phase-2 PR, not phase 1.
- **Review provenance**: record the *author* model in the review documents ("Author: prior plan" is not enough), so the two-different-LLM requirement can be checked.
